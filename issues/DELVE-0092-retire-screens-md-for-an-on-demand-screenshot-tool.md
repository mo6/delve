# Retire docs/SCREENS.md for an on-demand screenshot tool driven by the real renderer

## Summary

`docs/SCREENS.md` is 1049 lines of checked-in ASCII mock-ups, generated by `tools/screens.py`, a
second, hand-maintained implementation of Delve's screen layouts that duplicates locale data,
option-badge drawing, and geometry rules already living in `delve/ui/windows.py`. It exists to
answer "what does this screen look like", but as a parallel renderer it can *drift* from the real
one (DELVE-0018's peer review found exactly this: the mock shows a paid-removal badge as `x`, the
real renderer just dims the digit), and keeping the two in sync on every UI change is real,
recurring effort for no design benefit once an issue file already carries the change's rationale.
Retire the checked-in doc and its generator. Replace them with a small on-demand tool that drives
the *real* `RunState`/`Gate` and the *real* `delve/ui/windows.py` draw code against a headless
fake terminal, and prints the result with real ANSI colour, so a screen can be inspected during
development or after implementation without ever running the full curses game.

## Motivation / problem

`docs/SCREENS.md` says it itself, in its own header: "What a mock-up **can't** show: 16 colours,
and the lit/dim/black distinction." That has always been the file's central limitation, and now
it also has a maintenance cost that keeps growing as the UI grows: every screen-affecting change
needs its ASCII mock hand-regenerated and re-pasted, `tools/screens.py` re-implements enough of
`windows.py` to make that mock (its own `_options()`, its own locale table, its own wrapping) that
the two *can* disagree, and disagreement is invisible until someone happens to compare them by eye,
which is exactly what happened on DELVE-0018 (finding 1 of that review). Design rationale for a
screen change already belongs in the issue that made it (`issues/DELVE-NNNN-*.md`, per AGILE.md);
`docs/SCREENS.md` was answering "what does it look like now", a question a script driven by the
real code can answer more cheaply, more faithfully, and without upkeep, by just... running it.

## Stories

### As a maintainer, I want to see a real screen without playing the game, so that I can check a design during development or verify what shipped.

- Given a named scenario (e.g. the phishing MCQ with one option eliminated, the Dutch scroll, the
  tutorial's first screen), when I run the new tool for that scenario, then it drives a real
  `RunState` with real `Command`s to reach that exact panel state and prints the real
  `delve/ui/windows.py` draw output, not a re-implementation of it.
- Given the same scenario run twice, when I compare the two outputs, then they are byte-identical
  (the tool is deterministic, the same way the game itself is headlessly driven in tests).
- Given no scenario name, when I run the tool, then it lists every available scenario and exits
  cleanly (no partial output), the same discoverability `./tools.sh` itself gives for the tool
  list.

### As a maintainer, I want the output in colour, so that I can actually judge a palette or a dim/lit/black distinction without opening a terminal session of the game.

- Given a scenario that uses colour or the `A_DIM` attribute (an eliminated MCQ option, a struck
  pet consult, a lit-room tile), when the tool prints it, then the ANSI escapes it emits are built
  from the same `delve/ui/attrs.py` colour-pair mapping `windows.py` uses to paint the real
  terminal, not a second colour table.
- Given a terminal that doesn't support ANSI (piped to a file, `NO_COLOR` set), when the tool
  runs, then it still prints the plain characters (colour is additive, never required to read the
  layout).

### As a maintainer, I want the old mock-up and its generator gone, so that nothing is left to drift out of sync.

- Given `docs/SCREENS.md` and `tools/screens.py` are removed, when `./run-tests.sh` runs, then the
  `screens --check` gate step is gone too (there is nothing left to check), and every other step
  still passes.
- Given the removal, when the issue template and AGILE.md's Definition of Ready/Done are read,
  then their "screen impact" checkbox points at the new on-demand tool (run it, look at the
  output, note anything notable in the issue) instead of naming `docs/SCREENS.md`.
- Given archived issues that still link `docs/SCREENS.md` (history), when the removal lands, then
  those links are left as-is (they're a record of what was true when written, per AGILE.md's own
  "ids never move" spirit); only the *live* process docs (`AGENTS.md`, `issues/AGILE.md`,
  `issues/TEMPLATE.md`, `tools/README.md`) are updated to stop pointing at it.

## Non-goals

- `tools/infoscreen_mockups.py` (proposed, not-yet-built screens for a future issue like
  DELVE-0035) is a different problem: there is no real code to run yet for a screen that doesn't
  exist. It keeps its current hand-drawn-with-asserted-geometry approach; this issue does not
  touch it.
- No change to `delve/ui/windows.py`, `attrs.py`, or any real rendering code. The new tool is a
  consumer of the existing renderer, not a rewrite of it.
- No new CI gate. The whole point is that this tool is run *on demand*, not checked in and
  asserted on every `run-tests.sh`; nothing about it blocks a commit.
- Not a general screenshot/VHS-style recording tool or a golden-image diff system. A single
  static frame per scenario, printed to stdout, is the whole scope.

## Design notes / links

`tests/test_render.py` already has the load-bearing piece: `CursesEmu`, a minimal `stdscr` stand-in
that reproduces curses' `addstr` wrapping and the bottom-right-cell error, tracking both the
character grid and the attribute each cell was last written with. The real `delve/ui/windows.draw`
is exercised against it today purely for test assertions (e.g. the panel box stays well-formed).
The new tool reuses this exact mechanism, likely promoted out of `tests/test_render.py` into a
small shared module (`tools/_fakescreen.py` or similar, not part of the `delve` package, matching
`tools/README.md`'s "none of these are imported by it" rule) so both the tests and the tool share
one fake terminal rather than two.

Scenarios are named, headless command scripts against `new_run`/a parsed pack room, the same shape
`tests/test_stakes.py`, `tests/test_freetext.py`, and `tests/test_eliminate.py` already use to walk
to a keeper, open a lesson, or reach a particular question state (`_approach`, `_walk_beside_keeper`,
`_open_mcq`). Each scenario is a short Python function, not a DSL, since the existing test helpers
already are that vocabulary; a first pass should cover roughly the scenarios `docs/SCREENS.md`
currently hand-lists (tutorial first screen, keeper lesson, MCQ with an elimination, assertion,
explanation, failure/REPELLED, scroll in both locales, the money objects, the `?` help panel) so
nothing already-checked is lost, just no longer *committed*.

Colour: `delve/ui/attrs.py` holds the `Colour` enum and `bar_attr`/pair-setup Delve already uses;
the tool's ANSI writer maps that same table to SGR codes (`\033[3{n}m` etc., 16-colour to match the
game's own `curses.COLOR_*` set) rather than inventing a second palette, and reads `A_DIM` off each
cell to dim the corresponding ANSI attribute, so a dim/lit/black distinction (the thing `SCREENS.md`
could never show) is finally visible.

Process docs to update once the tool exists: `AGENTS.md` (the "mock-ups are generated" paragraph),
`issues/AGILE.md` (Definition of Ready/Done's "screen impact" bullets), `issues/TEMPLATE.md` (design
notes pointer), `tools/README.md` (`screens.py` entry becomes the new tool's entry), and
`run-tests.sh` (drop the `screens --check` step). `CHANGELOG.md` gets the usual entry. Locale
impact: none, the tool renders whatever locale a scenario asks for, same as `screens.py` did.

## Acceptance / verification

- A test drives the new tool's Python entry point (not just the CLI) for at least the MCQ,
  assertion, and tutorial-first-screen scenarios and asserts the printed grid is 100x30 and
  matches a fixture captured from the real `RunState`/`windows.draw` pair, proving it renders the
  actual code path rather than a re-implementation. Covers the first story.
- A test asserts the ANSI writer's colour codes for a known cell (e.g. an eliminated option's
  `A_DIM`) trace back to `delve/ui/attrs.py`'s own table, and that `NO_COLOR`/non-tty output still
  contains the same plain characters with no escape codes. Covers the second story.
- `docs/SCREENS.md` and `tools/screens.py` no longer exist in the tree; `run-tests.sh` has no
  `screens` step; `grep -rl 'docs/SCREENS.md'` over `AGENTS.md`, `issues/AGILE.md`,
  `issues/TEMPLATE.md`, `tools/README.md` (the live process docs) returns nothing, while archived
  issues under `issues/archive/` are left untouched. Covers the third story.
- `./run-tests.sh` passes.
